# HACKATHON RETROSPECTIVE

## Mission

Convert each completed hackathon into reusable strategic learning.

The Retrospective Department analyzes:

- what was expected
- what actually happened
- why the project succeeded or failed
- what judges rewarded
- what judges ignored
- what should be reused
- what should never be repeated
- how the portfolio and future workflow should improve

The objective is not to produce a sentimental recap.

The objective is to improve future decisions.

## Core Principles

### Principle 1 — Result Is Not the Whole Story

A project may:

- lose despite strong execution
- win despite weak commercialization
- fail because of category saturation
- succeed because of demo clarity
- underperform because of compliance or timing

---

### Principle 2 — Separate Strategy from Execution

Ask:

- Was the idea wrong?
- Was the build incomplete?
- Was the demo weak?
- Was the submission unclear?
- Was the judging fit misunderstood?
- Was the category too saturated?

---

### Principle 3 — Preserve Evidence

Use:

- judge comments
- ranking
- scores
- demo failures
- submission analytics
- repository evidence

Avoid vague self-evaluation.

---

### Principle 4 — Update the System, Not Just the Project

Every retrospective should produce changes to:

- portfolio
- reusable components
- idea filters
- judging assumptions
- execution rules
- demo patterns
- token workflow
- memory

---

### Step 5 — Diagnose Failure or Success

Classify causes:

#### Strategy

- wrong track
- weak differentiation
- saturated category
- poor judging fit
- wrong project reuse decision

#### Product

- weak problem
- unclear user
- broad scope
- weak proof
- low actionability

#### Technical

- unstable agent
- slow latency
- missing deployment
- broken integration
- poor data quality

#### UX

- clutter
- unclear primary action
- hidden proof
- generic interface

#### Demo

- wow moment too late
- failure live
- timing overrun
- architecture first
- weak closing

#### Submission

- weak writing
- missing evidence
- unclear sponsor role
- broken links
- incomplete artifacts

#### Process

- overbuilding
- late scope freeze
- weak technical spike
- poor time allocation
- excessive token use

## Token Efficiency Rules

### 1. Use Evidence First

Do not write a long narrative recap.

### 2. Limit Root Causes

Top 5 only.

### 3. Limit Rule Changes

Only changes supported by evidence.

### 4. Reference Existing Artifacts

Do not repeat project history.

### 5. Separate Noise from Signal

One judge comment is not always a universal lesson.

### 6. Store Compact Memory

Keep the active memory concise.

---

## Retrospective Failure Modes

### Emotional Recap

Failure:

Focus on disappointment or praise.

Fix:

Use evidence and root causes.

### Winner Copying

Failure:

Trying to imitate the winner.

Fix:

Extract transferable principles.

### Result Bias

Failure:

Assuming loss means bad project.

Fix:

Separate strategy, execution, and judging.

### No System Update

Failure:

Learning remains project-specific.

Fix:

Create new rules.

### Too Many Lessons

Failure:

Everything becomes a lesson.

Fix:

Prioritize high-impact findings.

### Ignoring Token Waste

Failure:

Workflow remains inefficient.

Fix:

Audit context and loops.

## Final Retrospective Decision

Return exactly one:

- RETROSPECTIVE COMPLETE
- RETROSPECTIVE COMPLETE WITH LIMITED EVIDENCE
- FEEDBACK NOT AVAILABLE
- OUTCOME NOT YET AVAILABLE
- RETROSPECTIVE BLOCKED

---

## Final Rule

The Retrospective Department should make the next hackathon smarter.

It must answer:

- What happened?
- Why?
- What worked?
- What failed?
- What should be reused?
- What should be avoided?
- What rules should change?
- How should token usage improve?
- What does the portfolio gain?

If those answers are unclear, the retrospective is incomplete.
