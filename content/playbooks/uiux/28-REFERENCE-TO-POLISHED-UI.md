# 28 — Reference to Polished UI

Purpose: transform videos, screenshots, templates, UI kits, and product references into polished, non-generic UI without blindly copying.

Workflow:
Reference → Deconstruct → Taste Layer → Design System → Build → Polish → Verify

## Use when

- Creating or improving a landing page.
- Rebuilding from a video or full-page screenshot.
- Improving a Wonder, Framer, Lovable, Claude Code, Cursor, or Codex UI.
- Making a dashboard less generic.
- Creating a portfolio case study page.
- Doing a client/local business glow-up.

## Step 1 — Reference strategy

Choose 1–3 sources.

```md
Reference strategy:
- Surface:
- Bottleneck:
- Sources to use:
- What to extract:
  - section rhythm
  - hero composition
  - CTA treatment
  - typography direction
  - color behavior
  - icon language
  - proof/evidence layout
  - mobile behavior
```

## Step 2 — Deconstruct

Extract patterns, not decoration.

Look for:
- section order;
- hierarchy;
- density;
- CTA placement;
- product/result framing;
- social proof;
- proof/evidence visibility;
- animation role;
- mobile simplification;
- visual motif.

## Step 3 — Taste layer

Apply Taste Skill, UI Skills, or anti-slop pass.

Check:
- Is the hero specific?
- Is the typography intentional?
- Are cards too generic?
- Is spacing consistent?
- Is the CTA obvious?
- Is the proof impossible to miss?
- Does the visual style serve comprehension?

## Step 4 — Design system / components

If building in React/shadcn, use Better Design or relevant UI kits.

If using Framer/Wonder/Lovable, use the reference as direction but preserve:
- project promise;
- evaluator path;
- proof labels;
- limitations;
- CTA hierarchy;
- mobile readability.

## Step 5 — Build handoff

Builder handoff must include:
- project name;
- one-line promise;
- surface type;
- reference sources;
- extracted patterns;
- section order;
- component names;
- typography direction;
- color roles;
- icon system;
- motion strategy;
- evidence card rules;
- responsive behavior;
- acceptance checks.

## Step 6 — Verify

Before shipping:
- proof labels remain readable;
- limitations are close to evidence;
- no simulated/stubbed work looks live;
- mobile preserves promise, CTA, result, evidence, limitations;
- screenshots are readable;
- visual risk supports the project rather than competing with it.
